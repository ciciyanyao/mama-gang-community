登录与游客权限（10/8 补充）：游客可看、参与才要求登录——社区类产品标准打法（工具类如记账/打卡/预约才强制登录；我们是内容类，渐进式降门槛）。微信登录分两层：① 静默层——进入小程序即 wx.login() → login 云函数换 openid → 自动查/建 users 记录，用户无感、无弹窗（每个微信用户天然有 openid）；② 交互层——用户能感知的"登录" = 设置头像昵称：2021 年后 getUserProfile 授权弹窗已废弃（只能拿匿名灰头像+"微信用户"），改用官方头像昵称填写能力（头像 <button open-type="chooseAvatar"> 弹头像选择器、昵称 <input type="nickname"> 唤起昵称快捷填充）。权限边界：列表/详情/案例库/树洞浏览全开；发帖/评论/点赞/收藏需登录。
为什么不用 uni-app / Taro：比赛只需微信一端、5 天窗口、成员技术栈未知；原生零构建链、官方文档与云开发无缝集成，出问题查资料最快。若后续要扩 H5 / 多端，再迁移 uni-app（Vue 语法）也不迟。Taro（React）对你们三人学习成本最高，不作考虑。

⑦ Git 协作规范（回答「Git 还是微信开发者工具内置？」）

直接回答：微信开发者工具内置的「版本管理」本身就是 Git 的图形化界面（可初始化仓库、提交、拉取/推送/抓取、创建/检出分支，支持 GitHub / Gitee / 微信代码管理 git.weixin.qq.com）。但它是"操作 Git 的工具"，不是远程仓库——3 人协作必须再有一个远端仓库。已定：GitHub 私有仓库 https://github.com/ciciyanyao/mama-gang-community.git（周勤希用 watt toolkit 加速器保证访问；备选 Gitee / 微信代码管理，换仓成本低）。结论：用 Git，且用「微信开发者工具 GUI + 命令行补充」结合。

分支模型（简化 Git Flow，3 人够用）

分支用途规则
main可演示的稳定版本受保护，禁止直接推送；只在里程碑（10/8 骨架、10/12 冻结）由负责人合并
dev开发主线日常合并目标；每人每天至少 pull 一次
feature/xxx每人每功能一个分支命名如 feature/forum-post、feature/tree-hole；完成后合并回 dev 并删除

每日工作流（5 步）

步骤操作说明
1git pull origin dev先同步，后开工；避免积压冲突
2git checkout -b feature/xxx从最新 dev 切功能分支
3小步提交每完成一个可运行的小单元即提交；commit 信息规范：feat: 发帖图文上传 / fix: 评论计数不同步 / docs: 更新数据模型
4合并回 dev先 pull dev → 解决冲突 → 合并 → 推送
5里程碑合并 main仅负责人操作，打 tag（v0.1 骨架 / v0.9 冻结）
